# BoutiqueDB — Swift/Turso Framework Specification

> A first-class Swift data layer for Turso that mirrors the ergonomics of
> Point-Free's SQLiteData/GRDB/StructuredQueries stack while exposing every
> Turso-only feature as a typed, macro-backed API.

---

## 1. Goals & Non-Goals

### Goals
- Provide the same developer-experience baseline as SQLiteData:
  `@BoutiqueFetchAll`, `@BoutiqueFetchOne`, migrations, typed queries,
  transactions, and `DatabaseMigrator`-style schema drift handling.
- Treat Turso-only capabilities (sync, CDC, MVCC, vector/FTS, materialized
  views, extensions, encryption, multi-process WAL) as first-class APIs, not
  "escape hatches".
- Use **StructuredQueries** as the SQL DSL/ORM backbone (schemas, query
  builders, aggregations, joins, insert/update/upsert/delete).
- Integrate cleanly with **SwiftUI Observation** and, for older OS versions,
  **Perception**.
- Support both local-only Turso and **Turso Cloud** sync in the same API.
- Macro-first: wrap schema, queries, and sync-aware observations in macros
  where Swift's macro system can safely generate the boilerplate; fall back
  to raw SQL/PRAGMA APIs when macros are not appropriate.

### Non-Goals
- This is not a GRDB/SQLiteData fork or wrapper; it is a new API surface
  that *learns from* those projects.
- We do not re-implement the Turso engine in Swift. The engine is consumed
  through a Swift binding/FFI layer (see §10).
- We do not hide every PRAGMA behind a type; "experimental" Turso features
  stay reachable via `database.execute(raw:)` for advanced usage.

## 3. Design Principles

1. **Common SQLite features → SQLData-style ergonomics, our naming.**
   - `Database` → `BoutiqueDatabase`
   - `@Table` → `@BoutiqueTable` (extends StructuredQueries `@Table`)
   - `@FetchAll` → `@BoutiqueFetchAll`
   - `DatabaseMigrator` → `BoutiqueMigrationPlan`
2. **Turso-only features → explicit, typed APIs.**
   - No hidden SQL generation unless a macro can do it safely.
   - Experimental features are marked `@_spi(BoutiqueExperimental)` or live in
     `BoutiqueDBTurso`.
3. **Observation is opt-out, not opt-in.**
   - Any fetch property wrapper works with `Observation` and `Perception`.
   - Background sync automatically invalidates relevant fetched results.
4. **Dependencies injection for the database handle.**
   - `\.boutiqueDatabase` dependency key lets tests and previews swap the
     underlying connection without changing app code.
5. **One API, three deployment shapes.**
   - `BoutiqueDatabase`, `BoutiqueSyncedDatabase`, and
     `BoutiqueRemoteDatabase` share the same read/write surface so app code
     does not branch for local vs. cloud.
6. **Async-first with structured concurrency.**
   - All blocking I/O runs on a cooperative thread pool.
   - Transactions use Swift `withThrowingTaskGroup` for nested savepoints.
7. **Type safety through StructuredQueries schemas.**
   - Schemas generated by `@BoutiqueTable` compile to table descriptors,
     column references, and Codable mappings.
8. **Escape hatches stay visible.**
   - `database.execute(raw:)` and `database.transaction { ... }` expose the
     underlying statement handle for features that are not yet typed.

## 4. API Details

### BoutiqueDatabase
The root handle. Opened with a path or an in-memory identifier.

```swift
let db = try await BoutiqueDatabase(path: path)
let inMemory = try BoutiqueDatabase.inMemory()
```

`BoutiqueDatabase` is `Sendable` and wraps a single connection queue.
Reads can overlap; writes are serialized.

### BoutiqueConfiguration
Mirrors SQLiteData's `Configuration` but adds Turso knobs:

```swift
BoutiqueConfiguration(
  url: .inMemory,
  encryptionKey: nil,
  journalMode: .wal,
  mvcc: false,
  cdc: false,
  extensions: [.uuid, .regexp, .time, .percentile]
)
```

Validation rules:
- `mvcc == true` and `cdc == true` together throw
  `BoutiqueError.cdcMutuallyExclusiveWithMVCC`.
- `journalMode == .mvcc` requires `mvcc == true`.

### Reads, Writes, and Transactions

```swift
let tasks: [Task] = try await db.read { reader in
  try await reader.fetch(Task.all.order(\.title))
}

try await db.write { writer in
  try await writer.insert(task)
}

try await db.transaction { tx in
  let id = try await tx.insert(task)
  try await tx.insert(Comment(taskID: id, text: "..."))
}
```

`read`, `write`, and `transaction` take a closure with `BoutiqueReader`,
`BoutiqueWriter`, or `BoutiqueTransaction`. All are async and throwing.

### Query Builder
`BoutiqueFetchRequest` wraps a `StructuredQueries` relation plus a
`BoutiqueDecoder` for the target type. Macros on `@BoutiqueTable` generate
static query helpers:

```swift
Task.all
Task.filter(\.isDone == false)
Task.filter(\.title.contains("Boutique"))
```

### Error Model
- `BoutiqueError.sqlError(SQLiteError)` for statement failures.
- `BoutiqueError.migrationError(...)` for plan drift.
- `BoutiqueError.syncError(SyncError)` for remote failures.
- `BoutiqueError.cdcMutuallyExclusiveWithMVCC` for invalid configuration.

## 5. Macros

### @BoutiqueTable
Expands a `StructuredQueries` `@Table`-conforming schema, a `Codable`
mapping, and a static relation:

```swift
@BoutiqueTable
struct Task: Identifiable {
  let id: UUID
  var title: String
  var isDone: Bool = false
}
```

Expansion:
- `Task.table` static schema reference.
- `Task.all`, `Task.filter(...)`, `Task.order(...)` helpers.
- `Insertion`, `Update`, `Upsert` value types for macro-checked writes.

### @BoutiqueFetchAll / @BoutiqueFetchOne
Property wrappers that observe a request and bind results to a SwiftUI or
Observable model:

```swift
@Observable
final class TaskListModel {
  @BoutiqueFetchAll(request: Task.all.order(\.title))
  var tasks: [Task] = []
}
```

The macro generates an `ObservationRegistrar` (or `PerceptionRegistrar` on
older OS) and invalidates when the underlying `BoutiqueDatabase` fires a
commit notification.

### @BoutiqueSelection
For custom projections that do not map to a table:

```swift
@BoutiqueSelection("SELECT title, COUNT(*) AS count FROM task GROUP BY title")
struct TitleCount: Decodable {
  let title: String
  let count: Int
}
```

## 6. Sync

### BoutiqueSyncedDatabase
A local database paired with a sync engine. The API surface matches
`BoutiqueDatabase` so views can consume either:

```swift
let synced = try await BoutiqueSyncedDatabase(
  localPath: path,
  syncConfiguration: .tursoCloud(
    url: "libsql://...",
    token: { ... }
  )
)
```

### BoutiqueSyncConfiguration
```swift
enum BoutiqueSyncConfiguration {
  case localOnly
  case tursoCloud(url: URL, token: () async throws -> String)
  case custom(SyncConfiguration)
}
```

The Turso Cloud case supports remote encryption, partial bootstrap, and
logical MVCC pull through the underlying sync engine.

### Sync Lifecycle
- `synced.sync()` — one-shot pull/push.
- `synced.startSync(interval:)` — periodic background sync.
- `synced.syncStatus` — `SyncStatus` stream.
- `synced.stopSync()` — cancel background work.

### Conflict and Encryption
- Conflicts are resolved by the Turso sync protocol (last-write-wins with
  vector clocks).
- Remote encryption key is separate from local encryption and is passed to
  the sync engine.
- Local encryption is **not** supported by Turso sync; attempting it raises
  `BoutiqueError.localEncryptionIncompatibleWithSync`.

## 7. Turso-Only Features

All Turso-only APIs live in `BoutiqueDBTurso` or behind
`@_spi(BoutiqueExperimental)`.

### Change Data Capture (CDC)
Per-connection, transaction-aware change stream:

```swift
let changes = try await db.cdcStream()
for try await change in changes {
  switch change {
  case .insert(let table, let rowID): ...
  case .update(let table, let rowID): ...
  case .delete(let table, let rowID): ...
  }
}
```

Requires `cdc` in `BoutiqueConfiguration`. Mutually exclusive with MVCC.

### MVCC
Snapshot isolation via `journalMode = .mvcc`:

```swift
let db = try await BoutiqueDatabase(
  path: path,
  configuration: .init(journalMode: .mvcc)
)
```

`BEGIN CONCURRENT` is exposed as `db.concurrentWrite { ... }`.
Experimental; hidden behind `@_spi(BoutiqueExperimental)`.

### Vector Search
Typed helpers for Turso vector functions:

```swift
let embedding: [Float] = ...
let nearest = try await db.vectorMatch(
  in: \Task.embedding,
  query: embedding,
  limit: 10,
  distance: .cosine
)
```

### Full-Text Search (FTS)
Tantivy-backed `USING fts` indexes:

```swift
try await db.createFTSIndex(for: \Task.title, \Task.notes)
let results = try await Task.match("Boutique sync")
```

`snippet()` is not available; `MATCH` is the supported predicate.

### Materialized Views
Incremental view maintenance:

```swift
try await db.create(MaterializedView<TaskSummary>.self)
```

Cannot reference other views or TEMPORARY tables; limited function support
is inherited from Turso's IVM implementation.

### Extensions
Scalar functions exposed as typed helpers:

```swift
UUID.v4()      // uuid4()
UUID.v7()      // uuid7()
String.regexp("...")  // regexp_like(...)
Date.timeInterval(...) // dur_ functions
```

Supported extensions: UUID, regexp, time, CSV, percentile, fuzzy, ipaddr.

### Encryption at Rest
`BoutiqueConfiguration.encryptionKey` maps to `PRAGMA cipher` / `PRAGMA
hexkey`. Requires the engine to be started with the experimental encryption
flag.

### Multi-Process WAL
For macOS apps that share a database with an extension or helper process:

```swift
BoutiqueConfiguration(multiProcessWAL: true)
```

Uses the `.tshm` sidecar file for cross-process WAL coordination.

## 8. Observation & SwiftUI Integration

`@BoutiqueFetchAll` and `@BoutiqueFetchOne` work with either
`Observation` (iOS 17+/macOS 14+) or `Perception` (back to iOS 15/macOS 12)
depending on the deployment target.

```swift
import BoutiqueDB
import Observation

@Observable
final class TaskListModel {
  @BoutiqueFetchAll(request: Task.all.order(\.title))
  var tasks: [Task] = []
}
```

Invalidation paths:
- Direct writes through the same `BoutiqueDatabase` update the commit
  generation counter.
- Sync pull merges remote frames and posts a `BoutiqueDatabase.didCommit`
  notification.
- CDC streams can be wired to invalidate specific tables.

## 9. Migrations

`BoutiqueMigrationPlan` replaces `DatabaseMigrator` with a DSL that ties
schema versions to `BoutiqueMigration` blocks:

```swift
try await db.migrate(using: BoutiqueMigrationPlan {
  BoutiqueMigration(1) { db in
    try await db.create(Task.self)
  }
  BoutiqueMigration(2) { db in
    try await db.alter(Task.self) { table in
      table.add(\.dueDate, type: .date)
    }
  }
})
```

Drift detection compares the current database schema against the expected
schema derived from registered `@BoutiqueTable` types. In debug builds, a
mismatch triggers an assertion; in release builds, it logs a warning and
continues.

## 10. Engine Binding / FFI Strategy

BoutiqueDB does not contain the Turso engine. It depends on a Swift binding
that exposes the C/libSQL API surface. M1 must settle one of these
strategies before higher-level work can land:

| Strategy | Description | Pros | Cons |
|----------|-------------|------|------|
| `turso-swift` official binding | Package from Turso | Maintained, supported | Does not exist yet |
| Custom C FFI over `libsql` | Wrap `libsql.h` with `swift-bindgen`/`cgg` | Full control | Maintenance burden |
| Rust crate via `swift-bridge` | Build the Rust core as a Swift package | Tightest integration | Long build times, complex SPM setup |

Recommended default: **custom C FFI** over the stable `libsql` C API,
because it ships today and can be swapped for an official
`tursodatabase/turso-swift` binding once it exists.

The `BoutiqueDatabase` protocol abstracts the binding so app code is
unaffected by the choice.

## 11. Milestone Roadmap

### M1 — Core local database
- `BoutiqueDatabase`, `BoutiqueConfiguration`, transactions.
- `@BoutiqueTable` and StructuredQueries integration.
- `BoutiqueMigrationPlan`, reads/writes, basic queries.
- In-memory and file-based databases.

### M2 — SwiftUI Observation
- `@BoutiqueFetchAll`, `@BoutiqueFetchOne`.
- `Observation` + `Perception` support.
- Invalidation through transaction commit hook.

### M3 — Sync
- `BoutiqueSyncedDatabase`, push/pull, sync stats.
- Remote encryption, partial bootstrap, logical MVCC pull.
- Sync → observation invalidation.

### M4 — Turso-only features
- FTS, Vector, Materialized Views.
- CDC and MVCC APIs.
- Extensions (UUID, regexp, time, CSV, percentile).
- Encryption at rest.
- Multi-process WAL.

### M5 — Polish
- Performance tests, macro tests, documentation, sample app.
- CI with `swift test` and integration tests against a local Turso CLI.

## 12. Known Limitations / "Bad Issues"

- **CDC and MVCC are mutually exclusive.** The framework should validate
  this at configuration time and throw `cdcMutuallyExclusiveWithMVCC`.
- **MVCC is experimental:** no GC, checkpoint blocks, recovery from logical
  log is not yet implemented. Keep it behind `@_spi` or a feature flag.
- **FTS uses Tantivy, not FTS5.** `snippet()` is missing; `MATCH` syntax
  is limited.
- **Sync local encryption is not supported** by the Turso sync engine. Use
  remote encryption for cloud databases.
- **Materialized views cannot reference other views** and have limited
  function support.
- **Postgres frontend is experimental** and intended for server-side /
  compatibility scenarios, not mobile apps.
- **No official Swift binding exists yet.** M1 must include the FFI
  strategy before other work can land.

## 15. Quick-Start Example

```swift
import BoutiqueDB
import BoutiqueDBSync

@BoutiqueTable
struct Task: Identifiable {
  let id: UUID
  var title: String
  var isDone: Bool = false
}

@Observable
final class TaskListModel {
  @BoutiqueFetchAll(request: Task.all.order(\.title))
  var tasks: [Task] = []
}

let db = try await BoutiqueDatabase(path: path)
try await db.migrate(using: BoutiqueMigrationPlan {
  BoutiqueMigration(1) { db in
    try await db.create(Task.self)
  }
})

var task = Task(id: uuid, title: "Write BoutiqueDB spec")
try await db.write { writer in
  try await writer.insert(task)
}
```

Sync-enabled variant:

```swift
let synced = try await BoutiqueSyncedDatabase(
  localPath: path,
  syncConfiguration: .tursoCloud(
    url: "libsql://...",
    token: { ... }
  )
)
```
